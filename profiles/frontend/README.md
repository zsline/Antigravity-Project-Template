# Профиль Frontend-проектов

## 1. Назначение

Профиль содержит дополнительные правила для frontend-приложений и пользовательских интерфейсов. Он дополняет общие правила `AGENTS.md`.

## 2. Документация проекта

В зависимости от масштаба проекта координатор определяет необходимость следующих документов:

- `PROJECT.md` — назначение продукта и границы MVP.
- `REQUIREMENTS.md` — требования и пользовательские сценарии.
- `ARCHITECTURE.md` — компоненты и структура приложения.
- `API.md` — контракты серверного API, если оно используется.
- `WORK_PLAN.md` — этапы разработки.
- `TASKS.md` — реестр задач.
- `QUALITY_CHECKLIST.md` — критерии качества.

## 3. Технологический стек

До разработки определить:

- основной язык и фреймворк;
- систему сборки;
- менеджер пакетов;
- библиотеку компонентов, если она нужна;
- маршрутизацию;
- управление состоянием;
- инструменты тестирования;
- целевые браузеры и устройства.

Версии зависимостей выбираются с учётом совместимости и фиксируются в проекте.

## 4. Архитектура интерфейса

При проектировании определить:

- страницы и маршруты;
- повторно используемые компоненты;
- структуру компонентов и их ответственность;
- источники данных;
- обработку состояния и ошибок;
- границы взаимодействия с API;
- правила размещения стилей и ресурсов.

Не создавать универсальные компоненты, если они не решают реальную повторяющуюся задачу.

## 5. UI/UX

- Согласовать основные пользовательские сценарии до реализации.
- Поддерживать единообразие интерфейса.
- Учитывать мобильные и десктопные экраны.
- Предусматривать состояния загрузки, пустых данных, ошибок и успешных операций.
- Не полагаться исключительно на цвет для передачи важной информации.
- Сохранять доступность интерактивных элементов.
- Не менять согласованный дизайн без обоснования и координации.

## 6. Работа с API

- Использовать согласованные контракты API.
- Обрабатывать ошибки и отсутствие соединения.
- Не считать клиентскую валидацию заменой серверной.
- Не хранить секретные ключи в браузерном коде.
- Не предполагать, что запрос всегда завершается успешно.
- Учитывать отмену запросов и устаревшие ответы, если это важно для сценария.

## 7. Безопасность

- Не вставлять недоверенный HTML без безопасного механизма обработки.
- Проверять границы доверия между клиентом и сервером.
- Не хранить чувствительные данные в браузерном хранилище без обоснования.
- Не полагаться на скрытие элемента интерфейса как на контроль доступа.
- Проверять внешние ссылки, перенаправления и обработку пользовательского ввода.

## 8. Производительность

- Избегать ненужных повторных рендеров и вычислений.
- Оптимизировать изображения и ресурсы.
- Загружать тяжёлые компоненты по необходимости, если это оправдано.
- Не добавлять крупные зависимости без оценки пользы.
- Проверять размер сборки и скорость загрузки критических страниц.

## 9. Тестирование

В зависимости от проекта проверять:

- поведение отдельных компонентов;
- пользовательские сценарии;
- формы и валидацию;
- адаптивность;
- доступность;
- обработку ошибок API;
- совместимость целевых браузеров;
- отсутствие регрессий.

## 10. Документация и согласования

При изменении маршрутов, публичных компонентов, форматов данных или контрактов обновлять соответствующие документы.

Изменения общих компонентов и дизайн-системы согласовывать с координатором, если они затрагивают другие задачи.

## 11. Полезные источники

- MDN Web Docs: https://developer.mozilla.org/
- Web Content Accessibility Guidelines: https://www.w3.org/WAI/standards-guidelines/wcag/

Выбирай конкретные инструменты проверки с учётом фактического стека проекта.
