# Профиль API-проектов

## 1. Назначение

Профиль предназначен для самостоятельных API-сервисов и интеграционных систем. Он дополняет общие правила `AGENTS.md`.

## 2. Документация проекта

Координатор определяет необходимость следующих документов:

- `PROJECT.md` — назначение сервиса и его границы.
- `REQUIREMENTS.md` — функциональные и нефункциональные требования.
- `ARCHITECTURE.md` — компоненты и взаимодействия.
- `API.md` — контракты API.
- `DATABASE.md` — структура данных, если используется хранилище.
- `WORK_PLAN.md` — план разработки.
- `TASKS.md` — реестр задач.
- `QUALITY_CHECKLIST.md` — критерии качества.

## 3. Проектирование API

1. Определить потребителей API и основные сценарии использования.
2. Зафиксировать контракты запросов и ответов до параллельной реализации зависимых компонентов.
3. Для каждой операции определить входные данные, успешные ответы и ошибки.
4. Единообразно описывать ошибки и валидацию.
5. Определить правила версионирования и совместимости.
6. Документировать пагинацию, фильтрацию, сортировку и ограничения запросов, если они применяются.
7. Не менять согласованный контракт без координации с владельцами зависимых компонентов.

## 4. Архитектура

По необходимости выделять:

- маршрутизацию и обработчики запросов;
- бизнес-логику;
- слой доступа к данным;
- интеграционные адаптеры;
- аутентификацию и авторизацию;
- фоновые задачи;
- логирование и мониторинг.

Выбор технологий и слоёв зависит от требований проекта. Не создавать абстракции без обоснования.

## 5. Безопасность

- Использовать HTTPS в соответствующих окружениях.
- Проверять аутентификацию и права доступа на сервере.
- Валидировать входные данные.
- Не раскрывать внутренние исключения и секреты клиентам.
- Ограничивать частоту запросов там, где это необходимо.
- Защищать чувствительные операции от повторного выполнения.
- Не хранить ключи, пароли и токены в исходном коде.
- Учитывать риски доступа к чужим ресурсам через подмену идентификаторов.

## 6. Надёжность и производительность

- Определить тайм-ауты внешних запросов.
- Продумать обработку недоступности зависимостей.
- Использовать повторные попытки только там, где они безопасны.
- Для повторяемых операций определить необходимость идемпотентности.
- Учитывать пагинацию и ограничения объёма данных.
- Для длительных операций рассмотреть фоновые задачи.

## 7. Тестирование

В зависимости от проекта предусмотреть:

- тесты бизнес-логики;
- тесты API-контрактов;
- тесты авторизации;
- тесты валидации и ошибок;
- интеграционные тесты;
- проверки совместимости;
- тесты критических сценариев.

## 8. Правила параллельной разработки

- Согласовать контракты до одновременной реализации клиента и сервера.
- Назначать одного ответственного за каждый изменяемый контракт.
- Разделять ответственность за независимые конечные точки и модули.
- Изменения общих схем и форматов согласовывать с координатором.
- Не считать успешную сборку доказательством корректности API.

## 9. Документация

При изменении контрактов обновлять `API.md` и связанные тесты.

Значимые решения фиксировать в `DECISIONS.md` и отдельных документах `docs/decisions/`.

## 10. Полезные спецификации

- OpenAPI: https://www.openapis.org/
- JSON Schema: https://json-schema.org/

Используй эти спецификации, если они подходят выбранному стеку и масштабу проекта.
