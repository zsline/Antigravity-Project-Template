# Профиль WordPress

## 1. Назначение

Профиль содержит дополнительные правила для разработки сайтов, тем и плагинов на WordPress. Он дополняет общие правила `AGENTS.md`, но не заменяет их.

## 2. Обязательные документы проекта

Координатор определяет необходимость следующих документов:

- `PROJECT.md` — описание продукта и границы MVP.
- `REQUIREMENTS.md` — требования.
- `ARCHITECTURE.md` — архитектура темы, плагинов и интеграций.
- `DATABASE.md` — структура данных и использование API WordPress.
- `WORK_PLAN.md` — план разработки.
- `TASKS.md` — реестр задач.
- `QUALITY_CHECKLIST.md` — критерии качества.

## 3. Правила работы с WordPress

1. До начала разработки определить версию WordPress, PHP и используемых зависимостей.
2. Использовать официальную документацию и проверять совместимость решений.
3. Соблюдать WordPress Coding Standards.
4. Не изменять ядро WordPress и код сторонних плагинов напрямую.
5. Не размещать бизнес-логику в шаблонах представления.
6. Не создавать собственный механизм там, где стандартные API WordPress подходят задаче.
7. Новые зависимости добавлять только при наличии обоснования.
8. Учитывать совместимость с активной темой, плагинами и редактором блоков.

## 4. Структура ответственности

При необходимости выделять следующие компоненты:

- Theme — оформление и представление.
- Plugin — функциональность, независимая от конкретной темы.
- Templates — шаблоны страниц и записей.
- Template Parts — повторно используемые части шаблонов.
- Blocks — блоки редактора, если используются.
- REST API — внешние и внутренние API, если нужны.
- Admin UI — интерфейс администрирования.
- Tests — автоматизированные проверки.

Не создавать дополнительные уровни абстракции без необходимости.

## 5. Безопасность

- Проверять права пользователя через подходящие механизмы WordPress.
- Валидировать и очищать входные данные в соответствии с контекстом.
- Экранировать данные при выводе.
- Использовать nonces для защиты соответствующих действий, учитывая, что nonce сам по себе не заменяет авторизацию.
- Подготавливать SQL-запросы безопасным способом.
- Проверять доступ к REST API и AJAX-обработчикам.
- Не хранить секреты в репозитории.
- Не отключать проверки безопасности ради упрощения реализации.

## 6. Работа с данными

- Использовать стандартные API WordPress, когда это уместно.
- Для собственных типов записей, таксономий и метаданных документировать назначение и ограничения.
- Изменение схемы пользовательских таблиц сопровождать контролируемой процедурой обновления.
- Учитывать префикс таблиц и возможность его изменения.
- Не предполагать, что идентификаторы или структура данных одинаковы на всех окружениях.

## 7. Производительность

- Проверять количество и стоимость запросов к базе данных.
- Избегать ненужных запросов и повторных вычислений.
- Применять кеширование только с понятными правилами инвалидации.
- Подключать CSS и JavaScript только там, где они нужны.
- Проверять производительность с учётом активных плагинов и темы.

## 8. Проверки перед завершением задачи

В зависимости от проекта проверять:

- корректность PHP и JavaScript;
- совместимость с заявленными версиями;
- права доступа и безопасность;
- работу шаблонов, блоков и форм;
- отсутствие ошибок в логах;
- регрессионные сценарии;
- производительность критических страниц.

Не заявлять о выполнении проверок, которые фактически не запускались.

## 9. Документация

При изменении публичных функций, хуков, блоков, REST API, пользовательских типов записей или настроек обновлять соответствующие документы.

Значимые архитектурные решения фиксировать через `DECISIONS.md` и отдельные записи в `docs/decisions/`.

## 10. Официальные источники

- Документация WordPress: https://developer.wordpress.org/
- Руководство по стандартам кода: https://developer.wordpress.org/coding-standards/wordpress-coding-standards/
