# Создание нового проекта из шаблона

## Цель

Создать отдельную рабочую папку проекта на основе универсального шаблона, сохранив стандартизированное разделение: документация и управление проектом размещаются в корне, а исходный код приложения — во вложенной папке.

## 1. Целевая структура и создание папки проекта

1. Скопируй всю папку `Antigravity-Project-Template` в каталог для ваших проектов (например, `D:\web\Мои проекты\NewProject\`).
2. Переименуй скопированную корневую папку в название нового проекта.
3. Открой корневую папку проекта в Antigravity IDE.

### Архитектурный стандарт размещения файлов:
- **Корень проекта** (`NewProject/`): содержит инструкции, правила агентов, workflows, шаблоны документации, проектную документацию (`PROJECT.md`, `ARCHITECTURE.md`, `TASKS.md` и др.) и каталог задач `tasks/`.
- **Вложенная папка приложения** (`NewProject/newproject/`): содержит исключительно исходный код приложения, его локальные конфигурации, зависимости и тесты.

### Правило именования папки приложения:
Имя папки формируется из названия проекта в нижнем регистре (латиница, цифры, дефис; без пробелов и специальных символов), например: для проекта `NewProject` папка приложения называется `newproject/`.

> **Важно:** 
> - Не разрабатывай проект непосредственно внутри исходного шаблона.
> - На этапе создания проекта и первичного анализа папка приложения **не создаётся**.

## 2. Первичная настройка

1. Ознакомься с [README.md](../README.md) и [AGENTS.md](../AGENTS.md).
2. Изучи правила ролей в `.agents/rules/` и рабочие процессы в `.agents/workflows/`.
3. Ознакомься с доступными профилями в `profiles/README.md` (`laravel/`, `wordpress/`, `api/`, `frontend/`).
4. Укажи начальные сведения в `PROJECT_CONFIG.md` (название, имя будущей папки приложения в нижнем регистре, предполагаемый тип проекта, статус `discovery`).

## 3. Запуск исследования и подготовки (Discovery)

Все дальнейшие шаги подготовки проекта к реализации выполняются по основному регламенту:
👉 **`.agents/workflows/project-discovery.md`**

Для старта передай агенту-координатору задание из стартовой инструкции, дополнив его своей вводной (название, идея и цели):
👉 **`docs/templates/PROJECT_START_PROMPT.md`**

В рамках регламента discovery координатор:
- собирает цели продукта и требования пользователей (`docs/templates/PROJECT_TEMPLATE.md`, `docs/templates/REQUIREMENTS_TEMPLATE.md`);
- создаёт и заполняет документы по мере появления подтверждённой информации, не придумывая неизвестные требования;
- определяет технологический стек и фиксирует архитектуру (`docs/templates/ARCHITECTURE_TEMPLATE.md`, `docs/templates/DATABASE_TEMPLATE.md`);
- регистрирует архитектурные решения в `DECISIONS.md` по шаблону `docs/templates/DECISION_TEMPLATE.md`;
- формирует этапы в `WORK_PLAN.md` и реестр задач в `TASKS.md`.

> **Главное ограничение этапа Discovery:** до завершения подготовки требований, архитектуры и плана папка приложения не создаётся, код и зависимости не инициализируются.

## 4. Организация задач

- Подробные задания создаются непосредственно в каталоге `tasks/` (кроме `tasks/templates/`) на основе `tasks/templates/TASK_TEMPLATE.md`.
- В задачах на разработку границы изменений и пути к файлам кода явно адресуются внутри вложенной папки приложения (например, `newproject/src/...`, `newproject/app/...`).
- Подкаталоги по статусам не создаются: статус каждой задачи фиксируется в её файле и синхронно отображается в `TASKS.md`.
- Жизненный цикл задач регулируется регламентом `.agents/workflows/task-lifecycle.md`.

## 5. Допуск к разработке и старт реализации

Основная реализация начинается только после того, как:
1. Проведена проверка готовности по чек-листу `.agents/workflows/readiness-check.md`.
2. Координатор представил итоговый отчёт discovery.
3. Пользователь дал явное подтверждение готовности проекта к разработке.

### Первая задача реализации:
1. Создание вложенной папки приложения с именем проекта в нижнем регистре (`<project_name_lowercase>/`).
2. Инициализация выбранного стека, конфигураций и зависимостей строго внутри этой вложенной папки.
3. **Организация Git:** основной и единый Git-репозиторий располагается в корне проекта. Если генератор фреймворка создал вложенный каталог `.git/` внутри папки приложения, не удалять его автоматически. Сначала проверить, существует ли вложенный репозиторий и есть ли в нём нужная история или изменения. Удалять его разрешается только после проверки, если это новый репозиторий генератора без нужной истории и подтверждено, что основным будет Git в корне проекта.
