# Организация параллельной работы агентов

## 1. Цель

Организовать параллельное выполнение независимых задач без конфликтов в коде, документации и архитектурных решениях.

## 2. Роль координатора

Перед запуском параллельных задач координатор обязан:

1. Изучить зависимости между задачами.
2. Проверить, какие файлы и модули затрагивает каждая задача.
3. Выяснить, используют ли агенты общую рабочую копию или изолированные рабочие среды.
4. Назначить каждой задаче одного ответственного исполнителя.
5. Определить ожидаемый результат и критерии приёмки.
6. Зафиксировать границы изменений.
7. Выявить общие файлы и потенциальные конфликты.
8. Убедиться, что необходимые интерфейсы и контракты согласованы.

## 3. Когда задачи можно выполнять параллельно

Параллельное выполнение допустимо, если:

- задачи не зависят от незавершённых результатов друг друга;
- определены интерфейсы взаимодействия между компонентами;
- при общей рабочей копии агенты гарантированно не изменяют одни и те же файлы (запуск задач с пересекающимися файлами категорически запрещён);
- при изолированных рабочих средах интеграция проводится через согласованный Git-процесс;
- изменения одного агента не нарушают требования другой задачи;
- есть возможность независимо проверить результаты.

Если независимость не подтверждена, координатор должен сначала уточнить границы задач.

## 4. Когда задачи нужно выполнять последовательно

Последовательное выполнение предпочтительно, если:

- одна задача требует результатов другой;
- несколько задач меняют одну архитектурную основу;
- изменяется общая схема базы данных;
- одновременно затрагиваются маршруты, контракты API или общие компоненты;
- решение первой задачи может изменить объём второй.

## 5. Владение файлами

Для каждой задачи указывай:

- разрешённые для изменения файлы;
- файлы, которые можно читать, но нельзя изменять;
- файлы, требующие согласования;
- ответственного за интеграцию изменений.

Агент не должен расширять область изменений без согласования с координатором.

## 6. Общие файлы

Если несколько задач требуют изменения одного файла:

1. Объедини изменения в одну задачу; или
2. Назначь одного ответственного за этот файл; или
3. Раздели работу на последовательные этапы.

Не допускай одновременного редактирования общего файла без явного плана интеграции.

## 7. Контракты между компонентами

До начала параллельной разработки согласуй необходимые контракты:

- входные и выходные данные;
- интерфейсы и методы;
- структуру API-запросов и ответов;
- модель данных и правила валидации;
- обработку ошибок;
- ответственность каждого компонента.

Если контракт меняется, координатор оценивает влияние на связанные задачи и уведомляет исполнителей.

## 8. Интеграция и работа с Git

После завершения параллельных задач координатор:

1. Проверяет отчёты агентов и фактический diff.
2. До утверждения конкретной стратегии ветвления координатор обязан проверить текущее состояние Git (статус рабочего дерева, diff) и не перезаписывать чужие изменения.
3. При изолированных рабочих средах интеграция проводится через согласованный Git-процесс.
4. Слияние изменений выполняется только после проверки изменений и успешного прохождения необходимых тестов.
5. Запускает общие интеграционные проверки и тесты совместной работы модулей.
6. При необходимости привлекает отдельного агента-ревьюера.
7. Обновляет документацию и статусы задач в `TASKS.md`.

## 9. Конфликты и блокировки

При конфликте агент должен:

1. Остановить конфликтующие изменения.
2. Описать проблему и затронутые файлы.
3. Указать, какие задачи заблокированы.
4. Передать информацию координатору.
5. Дождаться согласованного решения.

Агент не должен самостоятельно отменять чужие изменения или выполнять опасные операции с Git.

## 10. Правило минимального параллелизма

Не запускай максимальное количество агентов просто потому, что такая возможность доступна.

Выбирай минимальное количество параллельных исполнителей, которое сокращает сроки без существенного роста конфликтов, повторной работы и затрат на интеграцию.
