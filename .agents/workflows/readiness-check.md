# Проверка готовности проекта к разработке

## Цель

Определить, можно ли начинать основную реализацию проекта или сначала необходимо уточнить требования, принять решения и подготовить документацию.

## 1. Проверка требований

- [ ] Цель проекта и решаемая проблема описаны в `PROJECT.md`.
- [ ] Определены основные категории пользователей.
- [ ] Описаны ключевые пользовательские сценарии.
- [ ] Определены границы MVP.
- [ ] Зафиксированы функциональные и нефункциональные требования.
- [ ] Неоднозначные требования уточнены или явно отмечены как открытые вопросы.

## 2. Проверка архитектуры

- [ ] Выбран и согласован технологический стек.
- [ ] Подготовлен `ARCHITECTURE.md`.
- [ ] Согласована целевая двухуровневая структура: корень (управление и документация) и вложенная папка приложения с именем в нижнем регистре (`<project_name_lowercase>/`).
- [ ] Определены основные модули и их ответственность.
- [ ] Определены границы взаимодействия между модулями.
- [ ] Подготовлен `DATABASE.md`, если проект использует базу данных.
- [ ] Критические технические риски исследованы.
- [ ] Существенные решения записаны в `DECISIONS.md`.

## 3. Проверка плана

- [ ] Подготовлен `WORK_PLAN.md`.
- [ ] Этапы разбиты на небольшие задачи.
- [ ] Для задач определены критерии приёмки.
- [ ] Определены необходимые проверки и тесты.
- [ ] Указаны зависимости между задачами.
- [ ] Определены файлы и области изменений для задач.
- [ ] Возможности параллельной работы проверены на конфликты.

## 4. Проверка окружения

- [ ] Определён способ запуска проекта.
- [ ] Зафиксирована рабочая директория команд приложения (вложенная папка `<project_name_lowercase>/`, а не корень).
- [ ] Подтверждено, что единый репозиторий Git размещается в корне проекта.
- [ ] Зафиксированы требования к окружению.
- [ ] Определён способ управления зависимостями.
- [ ] Определён способ запуска тестов.
- [ ] Необходимые инструменты доступны либо описан порядок их установки.


## 5. Классификация проблем

Каждый незакрытый пункт классифицируй:

- **BLOCKER** — без решения нельзя безопасно или корректно начать соответствующую работу.
- **WARNING** — работу можно начать, если ограничение и последствия задокументированы.
- **INFO** — необязательное улучшение, которое не блокирует разработку.

Не считай все открытые вопросы блокирующими автоматически. Оценивай их влияние на конкретные задачи.

## 6. Итоговый статус

Используй один из статусов:

- `NOT_READY` — есть блокирующие вопросы.
- `READY_WITH_WARNINGS` — блокирующих вопросов нет, ограничения задокументированы.
- `READY` — обязательные проверки пройдены, критические вопросы решены.

## 7. Действия координатора

1. Проверь каждый пункт и укажи подтверждение из документации.
2. Составь список блокеров и предупреждений.
3. Для каждого блокера создай задачу или запроси уточнение у пользователя.
4. Не отмечай пункты выполненными только на основании предположений.
5. Повтори проверку после устранения блокеров.
6. Представь результат пользователю и запроси подтверждение перед началом основной реализации.

## Главное правило

Статус готовности должен отражать фактическое состояние документации и проекта, а не желание быстрее перейти к написанию кода.
