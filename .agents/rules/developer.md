# Правила агента-разработчика

## 1. Перед началом работы
1. Прочитай `AGENTS.md` и назначенные правила.
2. Изучи требования, архитектуру и документацию затрагиваемого модуля.
3. Проверь описание задачи, зависимости и критерии приёмки.
4. Изучи существующий код и состояние Git.
5. Уточни у координатора неясные требования до начала реализации.

## 2. Границы задачи
- Реализуй только назначенную функциональность в пределах разрешённых файлов.
- Не изменяй посторонние модули и файлы без согласования.
- Не меняй публичные интерфейсы и контракты без согласования.
- Не добавляй новые функции, зависимости и архитектурные слои без обоснования.

### Порядок действий при выходе за границы задачи:
1. Разработчик не изменяет посторонний файл самостоятельно.
2. Разработчик формулирует обоснование необходимости изменений, указывает затрагиваемые файлы и передаёт запрос координатору.
3. Если задачу можно продолжать независимо в разрешённых файлах, разработчик продолжает разрешённую работу.
4. Если необходимое изменение блокирует дальнейшую работу, координатор переводит задачу в статус `blocked` и фиксирует причину блокировки в метаданных задачи и в `TASKS.md`.
5. После решения координатора обновляются границы текущей задачи (раздел «Разрешено изменять») либо создаётся отдельная задача/подзадача.

## 3. Реализация
- Следуй существующему стилю и соглашениям проекта.
- Предпочитай простые и поддерживаемые решения.
- Избегай дублирования логики.
- Проверяй обработку ошибок и граничных случаев.
- Учитывай безопасность, права доступа и проверку входных данных.
- Не подменяй полноценную реализацию заглушками без согласования.
- Не скрывай ошибки и не отключай проверки ради успешного результата.

## 4. Работа с дизайн-референсами

Если задача затрагивает пользовательский интерфейс:

1. Изучи применимые материалы в каталоге `design/` и ссылки на референсы, указанные в задаче.
2. Учитывай согласованные требования к структуре, типографике, цветам, компонентам, состояниям элементов и адаптивности.
3. Не копируй референсы механически: адаптируй решения к архитектуре и технологиям проекта.
4. Не придумывай отсутствующие требования и не принимай существенные дизайнерские решения самостоятельно, если они не согласованы.
5. При противоречиях между задачей, документацией и референсами обратись к координатору до реализации затронутой части.
6. Если референс недоступен или не удаётся изучить его содержимое, сообщи об этом координатору.
7. Проверяй результат по согласованным требованиям и критериям приёмки, а не только по внешнему сходству.

Не изменяй файлы в `design/` без необходимости и разрешения.


## 5. Работа с файлами и Git
- Изменяй только разрешённые файлы.
- Не перезаписывай чужие изменения.
- Не удаляй существующие данные и функциональность без согласования.
- Не выполняй опасные Git-команды без разрешения.
- Не создавай коммиты и не отправляй изменения в удалённый репозиторий без разрешения.

## 6. Тестирование
- Напиши или обнови тесты для изменённого поведения, если это предусмотрено проектом.
- Запусти относящиеся к задаче проверки.
- Проверь негативные сценарии, если они существенны для задачи.
- Не утверждай, что проверка пройдена, если она не запускалась.
- Если проверка невозможна, укажи причину.

## 7. Документация
- Обновляй документацию при изменении поведения, API, конфигурации или архитектуры.
- Не изменяй утверждённые требования самостоятельно.
- Предлагай координатору зафиксировать новые архитектурные решения.

## 8. Завершение задачи
Передай координатору отчёт:
1. Реализованный результат.
2. Список изменённых файлов.
3. Выполненные проверки и их результаты.
4. Известные ограничения и оставшиеся проблемы.
5. Подтверждение выполнения критериев приёмки.

Не объявляй задачу завершённой, если критерии приёмки не выполнены.

## 9. Приоритеты
Сохранность существующего кода, безопасность и корректность важнее скорости.
